# LightRAG 选型验证执行计划

## 1. 文档目的

本文档用于指导 LightRAG 在隐私法律法规、公司制度和项目要求等垂直知识场景中的选型验证工作。

本次验证最终需要回答四个决策问题：

1. LightRAG 相比普通向量 RAG，是否显著提升问答准确性？
2. LightRAG 是否能提升条件判断、跨文档组合和多跳问题的逻辑性？
3. LightRAG 的在线响应速度是否满足业务要求？
4. LightRAG 应直接采用、改造后采用，还是不采用？

验证必须能够区分问题来自检索、知识组织、答案生成还是系统性能，不能只通过少量演示问题主观判断方案效果。

---

## 2. 验证范围

### 2.1 本轮包含的内容

- 法律法规、公司制度、项目要求三类知识的入库和查询。
- 普通向量 RAG 与 LightRAG 的对照实验。
- 简单事实、精确条款、条件与例外、跨文档推理、版本冲突、知识缺失等问题。
- 检索准确性、答案准确性、逻辑性、引用质量和拒答能力。
- 首字延迟、完整响应时间、检索耗时、并发性能和失败率。
- 失败案例分析以及必要的优化或改造建议。

### 2.2 本轮暂不作为重点的内容

- 大规模实时入库性能。
- 面向最终用户的完整产品界面。
- 全量生产知识迁移。
- 未经数据支持的复杂 Agent 工作流。
- 在验证结论形成前进行大规模架构改造。

### 2.3 基本原则

- 先确定评价标准，再开始调优。
- 先评估检索，再评估生成，避免把两类问题混在一起。
- 对照实验一次只改变一个主要变量。
- 开发集用于调优，盲测集只用于最终验证。
- 法律和制度类标准答案必须由领域人员确认。
- 重要结论必须能够回溯到原始文档和实验记录。
- 敏感原始文档和真实用户问题默认不提交到 Git；仓库只保存脱敏数据、结构定义、脚本和结果摘要。

## 3. 核心评价指标

### 3.1 准确性指标

| 指标 | 定义 | 评价对象 |
|---|---|---|
| 答案正确率 | 完全正确的问题数 / 总问题数 | 最终答案 |
| 证据召回率 | 被成功召回的必要证据数 / 全部必要证据数 | 检索结果 |
| 引用准确率 | 能够真实支撑对应结论的引用数 / 全部引用数 | 答案引用 |
| 完整回答率 | 所有必需结论均被覆盖的问题数 / 可回答问题数 | 最终答案 |
| 幻觉率 | 出现无证据事实、虚构条款或错误归因的问题数 / 总问题数 | 最终答案 |
| 正确拒答率 | 正确拒答的不可回答问题数 / 全部不可回答问题数 | 最终答案 |
| 版本适用正确率 | 正确使用有效版本的问题数 / 版本相关问题数 | 检索与答案 |

### 3.2 逻辑性指标

| 指标 | 定义 | 评价对象 |
|---|---|---|
| 逻辑正确率 | 推理链和结论均成立的问题数 / 逻辑类问题数 | 最终答案 |
| 条件完整率 | 正确覆盖前提、条件和例外的问题数 / 条件类问题数 | 最终答案 |
| 跨文档成功率 | 正确组合多份文档的问题数 / 跨文档问题数 | 检索与答案 |
| 结论可支撑率 | 可以由已引用证据推出的结论数 / 全部结论数 | 最终答案 |
| 自相矛盾率 | 答案内部或答案与证据矛盾的问题数 / 总问题数 | 最终答案 |

逻辑性人工评分采用三级制：

- 2 分：结论、条件、例外和推导过程均正确。
- 1 分：核心结论正确，但存在非关键遗漏或表达不清。
- 0 分：核心结论错误、推导不成立或遗漏关键条件。

### 3.3 性能指标

| 指标 | 定义 |
|---|---|
| P50/P95 首字延迟 | 从请求进入到收到第一个输出 Token 的时间 |
| P50/P95 完整响应时间 | 从请求进入到完整答案返回的时间 |
| P50/P95 检索耗时 | 不包含答案生成的检索阶段耗时 |
| 吞吐量 | 稳定状态下单位时间完成的请求数 |
| 超时率 | 超过规定时间未完成的请求数 / 总请求数 |
| 失败率 | 返回错误或无法完成的请求数 / 总请求数 |
| Token 消耗 | 单次请求的输入、检索上下文和输出 Token 数 |

### 3.4 待业务确认的验收阈值

以下值必须在正式实验前确认，不在计划阶段擅自假定：

```text
目标答案正确率：        [TBD]
目标证据召回率：        [TBD]
目标引用准确率：        [TBD]
目标逻辑正确率：        [TBD]
目标正确拒答率：        [TBD]
允许的总体幻觉率：      [TBD]
P95 首字延迟：          [TBD] ms
P95 完整响应时间：      [TBD] ms
目标并发量：            [TBD]
允许的失败率：          [TBD]
```

候选硬门槛：高风险盲测问题中的严重幻觉应为 0。严重幻觉包括虚构法规或条款、错误引用关键依据、把失效版本作为现行要求，以及把不适用范围的规则用于当前问题。

## 4. 总体交付物

验证完成后应得到以下产物：

1. 知识库文档清单及不可变语料快照。
2. 经过审核的问答评测集和盲测集。
3. 数据格式定义、标注规范和质量检查记录。
4. 普通向量 RAG 基线配置。
5. LightRAG 候选配置和完整版本信息。
6. 可重复运行的质量评测程序。
7. 可重复运行的性能测试程序。
8. 每次实验的配置、日志、原始结果和汇总报告。
9. 失败案例清单及根因分析。
10. 直接采用、改造后采用或不采用的最终建议。

---

## 5. 分阶段执行计划

## 阶段 0：确认业务边界和验收标准

### 要做什么

1. 确定知识库首批覆盖的法律地区、公司制度范围和项目范围。
2. 确定使用者类型，以及 Agent 会向 RAG 传递什么形式的问题。
3. 确定回答是否必须携带引用、引用需要精确到文档还是具体条款。
4. 确定知识冲突时的优先级规则，例如法律、公司制度和项目要求之间如何处理。
5. 确定现行版本、历史版本和未来生效版本的处理规则。
6. 确定性能 SLA、目标并发量、部署环境和允许使用的模型。
7. 确定哪些错误属于不可接受的严重错误。
8. 将第 3.4 节中的所有 `[TBD]` 转换为明确阈值。

### 交付物

- `validation-scope`：验证范围说明。
- `acceptance-criteria`：指标阈值和硬门槛。
- `rule-priority`：法规、公司制度和项目要求的优先级说明。

### 完成后验证什么

- 所有指标都有明确计算方法和通过阈值。
- “正确答案”的判断不存在未解决的业务歧义。
- 版本冲突、适用范围和知识缺失时的期望行为均有定义。
- 性能测试具有明确的硬件、模型、并发量和 SLA 前提。
- 产品、领域和技术相关人员对范围和标准达成一致。

### 退出条件

验收标准被确认并冻结为一个版本。未完成本阶段前，不进行正式方案评分。

---

## 阶段 1：建立源文档清单

### 要做什么

1. 收集候选法律法规、公司制度和项目要求。
2. 为每份文档分配稳定的 `document_id`。
3. 记录文件来源、所有者、版本、生效时间、失效时间、适用范围、权限范围和文件哈希。
4. 标记扫描件、表格、图片、附件、修订记录等特殊格式。
5. 识别重复文档、同名不同版文档和缺失附件。
6. 对真实敏感材料建立脱敏和访问控制方案。

### 交付物

- 文档清单 `document-manifest`。
- 文档分类和覆盖情况统计。
- 缺失文档、重复文档和敏感数据问题清单。

### 完成后验证什么

- 清单中的每份文档都能定位到唯一原始文件。
- 文件哈希能够识别内容变化。
- 每份文档都有类型、版本、生效时间和适用范围。
- 所有引用的附件实际存在。
- 同一文档的新旧版本能够被明确区分。
- 敏感文档没有被误提交到代码仓库。

### 退出条件

首批验证范围内的文档清单完整，且不存在会影响标准答案判断的关键缺失。

---

## 阶段 2：文档解析、清洗和规范化

### 要做什么

1. 将 PDF、Word、网页或扫描件转换成统一的可处理格式。
2. 保留标题层级、章节号、条款号、列表和表格结构。
3. 清除页眉、页脚、乱码和无意义重复内容。
4. 对扫描件执行 OCR，并保存 OCR 置信度或问题记录。
5. 为规范化内容保留原文位置映射，确保答案可以回溯原始文件。
6. 不在此阶段绑定特定 Chunk ID，避免评测数据依赖某一种切分策略。
7. 对日期、版本、机构名称和常用术语进行一致化处理，但不改写法律原义。

### 交付物

- 规范化文档。
- 原文到规范化文本的位置映射。
- 解析异常和人工修复记录。

### 完成后验证什么

- 随机抽检文档的正文、章节号和条款号是否完整。
- 表格、附件引用、条件列表和例外条款没有在解析中丢失。
- OCR 文本中的关键条款不存在数字、否定词或日期识别错误。
- 任何规范化段落都能回溯到原文件及位置。
- 相同内容没有因页眉页脚等原因大量重复。

### 退出条件

关键文档抽检通过，所有影响事实判断的解析错误已修复或明确记录。

---

## 阶段 3：建立知识语料快照

### 要做什么

1. 将首批文档组织为一次不可变的实验语料快照。
2. 明确包含哪些现行、历史和冲突版本。
3. 为快照生成版本号、文件哈希和统计信息。
4. 记录文档数、字符数、章节数、文档类型分布和版本分布。
5. 保存本次实验使用的解析工具和规则版本。

### 交付物

- `corpus-version`。
- 语料快照清单及摘要哈希。
- 语料覆盖报告。

### 完成后验证什么

- 同一快照可以在另一环境中得到相同的文档集合。
- 法规、公司制度和项目要求均达到预期覆盖范围。
- 已知的新旧版本、范围差异和跨文档关系在快照中真实存在。
- 后续任何文档变化都会产生新的快照版本，而不是静默覆盖。

### 退出条件

语料快照冻结，可以作为所有候选方案的共同输入。

---

## 阶段 4：设计问题覆盖矩阵

### 要做什么

1. 按问题类型设计覆盖比例：
   - 单文档事实型。
   - 精确条款型。
   - 条件与例外型。
   - 跨文档推理型。
   - 版本和冲突型。
   - 知识缺失型。
   - 歧义或错误前提型。
2. 为问题标记低、中、高风险。
3. 标记问题需要的文档类型和证据数量。
4. 标记单跳、多跳以及是否需要版本或适用范围判断。
5. 设计第一轮约 100 个问题的配额，方案稳定后再扩展。

### 建议的首轮分布

| 问题类型 | 数量 |
|---|---:|
| 单文档事实型 | 20 |
| 精确条款型 | 15 |
| 条件与例外型 | 20 |
| 跨文档推理型 | 20 |
| 版本和冲突型 | 10 |
| 知识缺失型 | 10 |
| 歧义或错误前提型 | 5 |

### 交付物

- 问题覆盖矩阵。
- 问题数量和风险等级配额。

### 完成后验证什么

- 每一种核心问题类型都有足够样本。
- 高风险问题不是全部集中在某一种文档或问题类型。
- 数据集同时包含简单问题和真正需要跨文档推理的问题。
- 知识缺失、错误前提和版本冲突没有被遗漏。
- 问题分布与实际 Agent 使用场景一致。

### 退出条件

问题覆盖矩阵通过业务和领域评审，可以指导问题收集。

---

## 阶段 5：收集和编写候选问题

### 要做什么

1. 优先收集经过脱敏的历史真实问题。
2. 由领域人员根据重要条款设计业务问题。
3. 使用模型辅助生成边界和改写问题，但不直接将生成内容作为标准答案。
4. 设计自然表达、简称、错别字、模糊指代等真实输入形式。
5. 设计无答案、错误前提、范围不适用和过期版本陷阱。
6. 去除只靠常识即可回答、无需知识库的无效问题。
7. 去除答案直接出现在问题文本中的泄漏样本。

建议来源比例：

- 50% 历史真实或真实业务问题。
- 30% 领域专家设计问题。
- 20% 边界、冲突和对抗问题。

### 交付物

- 未标注候选问题池。
- 每个问题的来源、类型、风险和难度标签。

### 完成后验证什么

- 问题符合覆盖矩阵配额。
- 没有完全重复或只有表面措辞不同的大量近重复问题。
- 问题表达接近真实用户，而不是全部照抄文档标题。
- 所有真实问题已经脱敏。
- 每个问题都能解释其业务价值和预期考察点。

### 退出条件

候选问题池数量达到目标的 1.2 至 1.5 倍，以便后续标注时淘汰低质量问题。

---

## 阶段 6：标注黄金答案、证据和推理要求

### 要做什么

为每个问题至少标注以下内容：

```json
{
  "case_id": "Q-001",
  "question": "问题文本",
  "question_type": "cross_document",
  "risk_level": "high",
  "answerable": true,
  "gold_answer": "经过确认的参考答案",
  "required_claims": ["必须包含的结论"],
  "forbidden_claims": ["不得出现的错误结论"],
  "evidence": [
    {
      "document_id": "doc-id",
      "version": "3.0",
      "section": "5.2",
      "text": "原文证据"
    }
  ],
  "reasoning_steps": ["必要推理步骤"],
  "expected_behavior": "answer"
}
```

具体工作包括：

1. 编写简洁、明确且不过度扩展的参考答案。
2. 标出所有必要结论 `required_claims`。
3. 标出典型严重错误 `forbidden_claims`。
4. 将证据定位到文档版本、章节和原文范围。
5. 为复杂问题标注必要推理步骤，但不要求模型输出隐藏思维过程；评测的是可观察的依据组合和结论。
6. 对不可回答问题标注正确行为，例如拒答、请求补充信息或指出错误前提。
7. 为存在多个合法表述的问题记录可接受答案边界。

### 交付物

- 带标准答案和证据的黄金评测集。
- 标注规范及示例。
- 标注疑问和裁决记录。

### 完成后验证什么

- 每个可回答问题都有至少一条明确原文证据。
- 跨文档问题包含全部必要证据，而不是只标其中一份文档。
- 标准答案没有超出证据能够支持的范围。
- `required_claims` 足以判断答案完整性。
- `forbidden_claims` 覆盖主要严重错误。
- 不可回答问题确实无法从当前语料快照中得到答案。
- 证据位置不依赖某一候选方案生成的 Chunk ID。

### 退出条件

所有入选问题完成标注，并且高风险问题完成领域人员复核。

---

## 阶段 7：执行数据集质量审核

### 要做什么

1. 由第二位审核者独立检查高风险问题的答案和证据。
2. 抽检中低风险问题。
3. 检查问题与答案是否存在歧义。
4. 检查证据能否完整推出结论。
5. 使用相似度检查发现重复和近重复问题。
6. 检查标签、文档 ID、版本、章节号和 JSON 格式。
7. 记录审核分歧并进行裁决。

### 交付物

- 数据质量报告。
- 审核分歧和裁决记录。
- 淘汰或返工的问题清单。

### 完成后验证什么

- 高风险问题双人复核完成率达到 100%。
- 所有问题都通过格式和引用完整性检查。
- 无法形成唯一评价标准的问题被修改或移除。
- 重复问题不会不成比例地影响最终分数。
- 随机抽取问题时，审核者能够仅依据语料和标注复现标准答案。

### 退出条件

数据质量达到预定标准，且不存在未裁决的高风险分歧。

---

## 阶段 8：划分并冻结数据集

### 要做什么

1. 将问题按 60% 开发集、20% 验证集和 20% 盲测集划分。
2. 按问题类型、风险等级和难度分层抽样。
3. 将相同事实或近重复问题放入同一个集合，避免泄漏。
4. 冻结盲测集，限制调优阶段访问。
5. 为问题集生成版本号、摘要哈希和变更记录。
6. 建立独立回归集，用于收录后续发现的失败案例。

### 交付物

- `development-set`。
- `validation-set`。
- `blind-test-set`。
- `regression-set`。
- 数据集版本和哈希。

### 完成后验证什么

- 三个集合的问题类型和风险分布合理。
- 不存在明显的近重复问题跨集合泄漏。
- 盲测集未被用于 Prompt、参数或路由策略调优。
- 使用相同版本和哈希可以复现完全相同的数据集。

### 退出条件

数据集正式冻结，任何修改均通过新版本进行。

---

## 阶段 9：建立普通 RAG 基线和 LightRAG 候选环境

### 要做什么

1. 固定模型、Embedding、Reranker、Prompt 和硬件环境。
2. 建立普通向量检索基线。
3. 建立 LightRAG 环境，并记录准确版本或提交号。
4. 使用同一语料快照分别入库。
5. LightRAG 至少测试 `naive` 与图谱增强模式；具体候选模式在小规模预实验后确定。
6. 统一回答格式、引用要求、上下文预算和超时配置。
7. 明确缓存策略并支持关闭缓存的实验。

### 交付物

- 基线配置文件。
- LightRAG 候选配置文件。
- 软件、模型、硬件和语料版本记录。
- 入库结果及异常日志。

### 完成后验证什么

- 两个方案使用完全相同的语料快照。
- 文档入库数量与清单一致，没有静默失败。
- 随机抽查的实体、关系和文本块可以回溯到原文。
- 同一请求可以明确选择候选配置和检索模式。
- 缓存能够被识别、清理或关闭。
- 重启环境后仍能复现查询结果和配置。

### 退出条件

基线和 LightRAG 均能稳定完成一组冒烟问题，且实验变量可控。

---

## 阶段 10：实现评测与观测能力

### 要做什么

1. 实现批量执行评测问题的 Runner。
2. 分别支持“只评检索”和“检索后生成答案”两种模式。
3. 保存召回文本、实体、关系、引用、最终 Prompt 和答案。
4. 保存模型、配置哈希、Token 数和各阶段耗时。
5. 实现证据召回率、引用准确率、答案正确率等指标计算。
6. 对逻辑性和复杂答案支持人工复核界面或可审阅结果文件。
7. 为自动评分器准备人工已知结果的小型测试样本。

每次请求至少记录：

```text
case_id
dataset_version
corpus_version
system_version
configuration_hash
retrieval_mode
retrieved_context
references
final_prompt
answer
input/output_tokens
retrieval_latency
first_token_latency
total_latency
automatic_scores
human_scores
error_type
```

### 交付物

- 可重复运行的评测程序。
- 统一实验结果格式。
- 自动评分器测试记录。

### 完成后验证什么

- 在相同配置和数据下可以重复执行同一实验。
- 检索失败和生成失败能够被分别识别。
- 证据召回率等指标通过人工构造样本验证计算正确。
- 延迟指标使用统一起止点和时钟。
- 失败请求不会被静默排除在统计之外。
- 实验结果能够追溯到具体配置和数据版本。

### 退出条件

评测程序通过自测，并能产出一份完整的小规模实验报告。

---

## 阶段 11：开展质量对照实验

### 要做什么

按以下顺序开展实验：

1. 运行普通向量 RAG 基线。
2. 运行 LightRAG 的 `naive` 模式，确认框架内普通检索表现。
3. 运行候选图谱模式。
4. 按问题类型比较准确性、逻辑性、引用和拒答表现。
5. 分析检索正确但生成错误，以及检索错误导致回答错误的比例。
6. 对随机样本和全部高风险样本进行人工复核。
7. 每个关键配置至少重复运行若干次，观察非确定性波动。

### 实验约束

- 第一轮只改变检索方案，不同时调整多个参数。
- 所有候选使用相同模型和回答 Prompt。
- 不使用盲测集进行调优。
- 自动评分结论必须经过人工样本校准。

### 交付物

- 按方案、问题类型和风险等级拆分的质量报告。
- 普通 RAG 与 LightRAG 的差异报告。
- 失败案例和根因分类。

### 完成后验证什么

- LightRAG 的质量提升能够定位到具体问题类型。
- 质量差异不是由模型、Prompt 或数据版本不同导致。
- 图谱模式是否真的改善跨文档和条件推理有明确证据。
- 简单问题是否因图谱噪声而退化得到验证。
- 所有严重错误均被单独列出，而不是隐藏在平均分中。

### 退出条件

能够明确说明 LightRAG 相比基线“在哪些问题上提升、提升多少、在哪些问题上退化”。

---

## 阶段 12：开展性能实验

### 要做什么

1. 分别测量检索、重排、Prompt 构造、首字和完整生成耗时。
2. 分别运行冷启动、稳定运行、缓存关闭和缓存命中场景。
3. 按简单问题、复杂问题、短答案和长答案拆分结果。
4. 在目标硬件和模型环境下执行并发测试。
5. 逐步提升并发量，观察延迟、吞吐、错误率和资源使用。
6. 普通 RAG 和 LightRAG 使用同样的负载模型。
7. 记录 CPU、内存、GPU、网络和外部模型服务限制。

### 交付物

- P50/P95/P99 延迟报告。
- 并发量、吞吐量和失败率报告。
- 缓存命中与未命中的差异报告。
- 各处理阶段的耗时拆解。

### 完成后验证什么

- 测试是在预热后的稳定状态下执行。
- 性能结果没有被查询缓存或限流重试掩盖。
- 所有方案使用相同问题集合、并发模型和生成长度要求。
- P95/P99 不受少量测试样本导致的统计失真影响。
- 能够识别瓶颈位于检索、关键词提取、图谱处理还是答案生成。
- 目标并发下的 P95 延迟、超时率和失败率是否满足阶段 0 的标准。

### 退出条件

可以量化 LightRAG 相对基线增加的延迟和资源成本，并判断是否满足 SLA。

---

## 阶段 13：错误分析与有限调优

### 要做什么

1. 将失败分为：
   - 文档解析错误。
   - 文档切分错误。
   - 实体或关系抽取错误。
   - 检索未召回。
   - 检索噪声过多。
   - 版本或范围选择错误。
   - 生成模型忽略证据。
   - 逻辑推导错误。
   - 引用错误。
   - 性能超时或系统错误。
2. 按频率、风险和修复成本排序。
3. 每轮只调整一个主要因素，例如切分、`top_k`、Reranker、上下文预算或 Prompt。
4. 每次调整后重跑开发集和回归集。
5. 如果不同问题的最优检索方式明显不同，再验证简单查询路由策略。
6. 记录每次调整对质量、延迟和成本的影响。

### 交付物

- 错误分类和优先级列表。
- 调优实验记录。
- 回归测试结果。
- 必要时形成 LightRAG 改造需求清单。

### 完成后验证什么

- 每项优化都解决了明确的高频或高风险问题。
- 修复某类问题时没有导致其他类型明显退化。
- 开发集提升能够在验证集复现。
- 回归集中已经修复的问题没有再次出现。
- 性能优化没有通过牺牲关键质量指标获得表面收益。

### 退出条件

候选配置冻结；继续调优的预期收益低于成本，或已经达到验收标准。

---

## 阶段 14：盲测、结论和选型建议

### 要做什么

1. 使用冻结配置运行盲测集。
2. 对高风险问题进行人工复核。
3. 对照阶段 0 的验收标准判断是否通过。
4. 汇总质量提升、性能代价、资源成本和工程复杂度。
5. 输出直接采用、改造后采用或不采用的建议。
6. 如果建议改造，明确改造项、收益、风险和优先级。

### 交付物

- 最终盲测报告。
- 质量与性能对照表。
- 严重错误清单。
- 技术选型结论。
- 后续实施或改造路线图。

### 完成后验证什么

- 盲测期间没有修改候选配置。
- 所有结果都能追溯到数据、语料、系统和配置版本。
- 每一个核心结论都有实验数据支持。
- 平均分没有掩盖高风险失败案例。
- 性能结果来自目标或等价部署环境。
- 最终建议清楚说明收益、代价、风险和适用边界。

### 退出条件

能够基于同一套数据和标准，对 LightRAG 做出可审计、可复现的选型决定。

## 8. 首轮工作顺序

计划确认后，按照以下顺序开始实际执行：

1. 完成阶段 0 的范围和阈值确认表。
2. 创建文档清单 Schema 和问题标注 Schema。
3. 接收首批候选文档并生成文档清单。
4. 对文档进行解析质量抽检并冻结第一版语料快照。
5. 建立问题覆盖矩阵。
6. 先制作 10 个完整标注样例，验证标注规范是否可用。
7. 标注规范稳定后扩展到首轮约 100 个问题。
8. 数据审核和切分完成后，再开始 LightRAG 环境及评测程序建设。

先制作 10 个高质量样例而不是直接制作 100 个问题，是为了尽早发现字段设计、证据粒度和评价标准中的问题，避免后续大规模返工。
