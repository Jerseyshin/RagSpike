# LightRAG 验证范围与验收标准

> 状态：Approved v1.0
>
> 批准日期：2026-10-18
>
> 批准角色：项目负责人（用户）
>
> 本文档对应《LightRAG 选型验证执行计划》的阶段 0。标记为“待确认”的内容在确认前不作为正式验收结论。

## 1. 已知背景

- 系统目标：建设面向自有 Agent 的垂直领域知识问答组件。
- 长期知识范围：隐私相关法律法规、公司章程及制度、项目要求。
- 首批验证知识范围：中国大陆隐私与数据合规法律法规知识库；其他法律领域、公司制度和项目要求不纳入首批。
- 首要目标：提高问答准确性、问答逻辑性和在线响应速度。
- 非关键目标：首轮验证不重点考察大规模实时入库速度。
- 候选技术：LightRAG。
- 对照方案：普通向量 RAG。

## 2. 本轮要做出的决策

本轮验证完成后必须对以下问题给出明确结论：

1. LightRAG 是否比普通向量 RAG 提供更高的答案准确性？
2. LightRAG 是否明显改善条件判断、例外识别、跨文档组合和多跳推理？
3. LightRAG 的质量收益是否值得增加的查询延迟和资源消耗？
4. 是否需要按问题类型在普通检索和图谱检索之间进行路由？
5. LightRAG 能否直接采用；若不能，需要哪些改造？

## 3. 验证范围

### 3.1 知识范围

| 类别 | 本轮范围 | 当前状态 |
|---|---|---|
| 隐私与数据合规法律法规 | 适用于中国大陆目标业务的法律、行政法规、部门规章、国家标准及相关监管要求 | 已确认纳入首批；其他法律领域排除，具体文件在阶段 1 确认 |
| 公司规则 | 公司章程、隐私制度、数据处理规范、审批流程 | 已确认不纳入首批 |
| 项目规则 | 项目要求、客户要求、补充约定、项目例外 | 已确认不纳入首批 |
| 历史版本 | 用于验证版本识别和历史时点问题 | 建议纳入少量代表性版本 |
| 未来版本 | 用于验证尚未生效规则不会被当作现行要求 | 建议纳入少量代表性版本 |

首轮语料的目标不是覆盖全部企业知识，而是覆盖真实查询中最重要、最容易出错的知识关系。

首批语料已确认全部来自互联网公开可查的数据源，可以发送到公网第三方模型 API。后续如引入公司制度、项目材料、真实用户查询或其他非公开信息，必须重新进行数据分级和模型服务合规评审，本次确认不得自动沿用。

### 3.2 用户和调用方

当前假设：

- 直接调用方是公司自有 Agent，而不是公开互联网用户。
- Agent 以自然语言向 RAG 发起查询。
- 第一轮已确认只验证中文单轮问题，以减少上下文记忆对结果的干扰。
- 多轮追问和会话记忆已确认在基础能力通过后单独验证。
- RAG 返回结构化答案、证据引用和必要的不确定性说明。

待确认：

- 是否存在英文或中英混合问题。
- 后续引入非公开材料时是否存在多个业务角色，以及不同角色能看到的文档范围。
- Agent 是否需要稳定的机器可读 JSON 响应。

### 3.3 查询类型

首轮包含：

- 单文档事实查询。
- 精确条款定位。
- 条件、前提和例外判断。
- 中国大陆不同法律、行政法规、部门规章、国家标准及监管要求之间的跨文档组合。
- 新旧版本及指定历史时点查询。
- 适用地区、组织、项目和数据类型判断。
- 知识库无答案时的拒答。
- 问题包含歧义、信息不足或错误前提时的澄清和纠错。

首轮不重点包含：

- 开放式法律研究和知识库外的网络检索。
- 对具体案件给出最终法律意见。
- 自动执行审批、删除、通知等业务动作。
- 复杂 Agent 工具调用链的端到端验证。

### 3.4 输出要求

已确认首批使用结构化 JSON 输出。候选结构如下，具体字段命名可在实现阶段调整，但不得降低引用粒度：

```json
{
  "answer": "简洁、直接的回答",
  "conditions": ["适用条件、例外或限制"],
  "references": [
    {
      "document_id": "document-id",
      "document_title": "法规名称",
      "version": "3.0",
      "effective_date": "2026-01-01",
      "section": "5.2",
      "excerpt": "直接支持结论的原文片段"
    }
  ],
  "confidence": "supported | insufficient | conflict",
  "clarification_needed": false
}
```

基本要求：

- 每个关键结论都必须有对应证据。
- 引用必须包含法规名称、当前有效版本或施行日期、具体条款编号和支撑结论的原文片段。
- 不得把“可能”“建议”表述为强制要求。
- 证据不足时不得补全或猜测事实。
- 存在冲突时应显示冲突及其来源，不得静默选择。
- 需要业务上下文才能判断时，应请求补充必要信息。

## 4. 规则优先级草案

### 4.1 总原则

首批只包含中国大陆法律法规知识。以下“约束累加”规则主要用于后续扩展到公司制度和项目要求时使用，本轮不将公司或项目规则纳入答案依据：

1. 适用法律法规构成不可突破的强制边界。
2. 公司制度可以在法律允许范围内增加更严格的内部要求。
3. 项目要求可以在其适用项目内增加更具体或更严格的要求。
4. 下层规则不能放宽上层规则的强制要求。
5. 任何材料是否适用，都必须先判断司法辖区、生效时间、组织范围、项目范围和数据类型。

示例：

```text
法律要求必须审批
公司制度要求审批并登记
项目要求审批、登记并进行额外安全评估

最终要求 = 审批 + 登记 + 额外安全评估
```

### 4.2 冲突处理

已确认处理规则：

- 下层规则比上层规则更严格：叠加更严格要求。
- 下层规则比上层强制规则更宽松：不得使用宽松规则规避上层要求。
- 同层规则范围不同：优先选择明确适用于当前地区、组织或项目的规则。
- 同层同范围的新旧版本：根据问题指定时点选择当时有效版本。
- 无法确定效力或适用范围：返回“证据冲突”或“需要澄清”，不得自主裁决。
- 法律或合同解释存在争议：标记需要法务或规则负责人确认。

上述规则已确认为首批冲突处理标准：先判断生效时间和适用范围；强制性要求不能被指南或推荐性标准放宽；多份有效规则同时适用时累加要求；无法判断效力或证据冲突时不自行裁决，必须返回冲突并提示人工确认。

### 4.3 时间规则

- 问题明确指定日期：使用该日期已经生效且尚未失效的规则。
- 问题未指定日期：默认使用查询发生时有效的最新版本。
- 未来生效版本：可以提示即将变化，但不得作为当前有效要求。
- 已失效版本：仅用于历史时点问题，不得用于当前要求。
- 生效信息缺失或冲突：要求澄清或交由人工判断。

### 4.4 首批法律法规的效力判断

首批评测需要由法律领域人员确认以下规则，RAG 系统不得仅根据文档名称自行推断：

- 法律、行政法规、部门规章、规范性文件及国家标准之间的效力和适用关系。
- 强制性标准与推荐性标准在具体问题中的不同作用。
- 综合性规则与特定行业、特定数据类型规则之间的适用关系。
- 同一规则的新旧版本、修订决定和生效时间。
- 监管问答、指南等材料是否可以作为答案依据，以及它们与正式规范文件的关系。

### 4.5 后续扩展待确认事项

- 法律法规、公司制度、合同和项目要求之间的正式优先级。
- “更具体规则”和“更严格规则”发生冲突时的裁决方式。
- 公司章程与普通公司制度之间的优先级。
- 客户合同、项目规范和公司制度冲突时的处理方式。
- 哪些冲突必须直接转人工，不允许系统给出结论。

## 5. 验收标准草案

以下质量和性能阈值均已确认为首轮正式验收标准。

### 5.1 质量阈值

| 指标 | 建议阈值 | 属性 | 说明 |
|---|---:|---|---|
| 总体答案正确率 | ≥ 90% | **已确认** | 完全正确，不以部分正确代替 |
| 高风险答案正确率 | ≥ 95% | **已确认** | 高风险问题单独统计 |
| 总体证据召回率 | ≥ 90% | **已确认** | 必要证据被召回的比例 |
| 高风险证据召回率 | ≥ 95% | **已确认** | 高风险问题单独统计 |
| 引用准确率 | ≥ 98% | **已确认** | 引用必须真实支持结论 |
| 逻辑正确率 | ≥ 90% | **已确认** | 条件和跨文档问题单独统计 |
| 正确拒答率 | ≥ 90% | **已确认** | 无答案、信息不足和不适用问题 |
| 总体幻觉率 | ≤ 2% | **已确认** | 任一无依据事实即计入 |
| 高风险严重幻觉 | 0 | **已确认硬门槛** | 参见第 6 节 |

除绝对阈值外，LightRAG 还应满足相对收益要求。候选规则：

- 在跨文档和逻辑类问题上，LightRAG 应相对普通向量 RAG 产生具有实际意义的提升。
- 如果质量提升很小但 P95 延迟明显增加，应优先保留普通向量 RAG。
- 如果收益集中在特定问题类型，应评估查询路由，而不是让所有请求统一走最重模式。

“具有实际意义的提升”需要在首轮基线结果出来后确认具体百分点，建议预先设定，避免看到结果后改变标准。

### 5.2 性能阈值

性能阈值强依赖模型、硬件、网络和答案长度。以下指标已确认为首轮正式性能 SLA，实际硬件、网络和服务版本将在环境部署时记录：

| 指标 | 建议阈值 | 属性 |
|---|---:|---|
| P95 首字延迟 | ≤ 2 秒 | **已确认** |
| P95 完整响应时间 | ≤ 8 秒 | **已确认** |
| P95 纯检索耗时 | ≤ 1 秒 | **已确认** |
| 目标并发量 | 10 | **已确认** |
| 目标并发下失败率 | ≤ 1% | **已确认** |
| 目标并发下超时率 | ≤ 1% | **已确认** |

测量约束：

- 记录答案输出长度，并避免候选方案使用完全不同的答案长度。
- 缓存未命中作为主要选型依据，缓存命中单独报告。
- 同时报告 P50、P95 和 P99，不使用平均值代替尾部延迟。
- 外部模型服务耗时必须包含在端到端耗时中，同时单独记录。
- 冷启动和稳定运行分别报告。

### 5.3 结果判定

#### 直接采用

- 达到全部硬门槛和主要质量、性能指标。
- 相比普通向量 RAG 在目标问题类型上有稳定收益。
- 不需要高风险、高复杂度的框架改造。

#### 改造后采用

- LightRAG 在复杂问题上有明确质量收益。
- 存在可以定位且能够控制的性能、版本、引用或路由问题。
- 改造成本低于采用其他方案的迁移和维护成本。

#### 不采用

- 相比普通向量 RAG 没有稳定质量收益。
- 存在无法接受的严重错误或不可控延迟。
- 所需改造会实质性替换 LightRAG 的主要能力。

## 6. 严重错误定义

出现以下任一种情况，应标记为严重错误，并单独报告：

1. 虚构不存在的法律、条款、制度或项目要求。
2. 引用内容与结论无关，或引用实际表达相反含义。
3. 把失效或尚未生效版本当作当前有效规则。
4. 把不适用于当前司法辖区、公司、项目或数据类型的规则用于回答。
5. 遗漏会改变结论的必要条件或例外。
6. 在证据明确冲突时隐瞒冲突并给出确定结论。
7. 知识库没有依据时生成确定性合规结论。
8. 向无权限调用者返回受限知识内容。

## 7. 实验控制条件

正式对照实验中应固定：

- 语料快照。
- 问题集版本。
- 生成模型及参数。
- Embedding 模型。
- Reranker 配置。
- 系统提示词和回答格式。
- 最大上下文和最大输出长度。
- 硬件、部署方式和外部模型服务。
- 缓存策略。

第一轮对照只改变检索方案。确定候选检索方案后，才分别开展切分、召回数量、重排、上下文预算和 Prompt 调优。

### 7.1 模型与部署环境选择原则

生成模型、Embedding 模型和部署方式当前尚未确认。确认前遵循以下原则：

1. 普通向量 RAG 与 LightRAG 必须使用相同的生成模型、Embedding 模型、Reranker 和模型参数。
2. 模型不能在同一轮对照实验中随检索方案一起变化，否则无法判断收益来自模型还是 LightRAG。
3. 生成模型必须稳定支持中文法律文本、结构化 JSON、流式输出和足够的上下文长度。
4. Embedding 模型必须适合中文及长句法律语义，并在同一语料快照上固定版本和维度。
5. 首批公开数据已允许发送到外部服务；后续引入非公开材料时，生成、Embedding 和 Reranker 必须重新按数据合规要求选型。
6. 质量实验和性能实验原则上使用同一部署环境；如果预研期使用云端 API、最终性能测试使用本地部署，必须分开报告，不能混合形成结论。
7. 性能结果必须记录模型名称和版本、量化方式、推理引擎、CPU/GPU、显存、网络及并发配置。

首轮部署方式已确认采用公网云端 API，以降低环境搭建成本并优先验证 LightRAG 的检索和回答质量。该决定仅适用于首轮公开数据验证，不代表最终生产环境采用云端部署；生产部署方式将在技术验证通过后单独评估。

模型选择前需要依次确认：

- 验证数据是否允许发送到外部模型 API：**已确认，首批公开数据允许**。
- 是否已有可用的本地 GPU 或企业内部模型服务。
- 可接受的模型调用成本或硬件预算。
- 是否要求全部组件离线运行。
- 生成模型和 Embedding 模型是否已有公司标准。

### 7.2 首轮候选模型组合

当前已具备 DeepSeek API Key。基于 DeepSeek 和 LightRAG 的官方能力说明，首轮候选组合为：

| 角色 | 候选模型或方案 | 模式 | 选择理由 | 状态 |
|---|---|---|---|---|
| 最终回答 QUERY | `deepseek-v4-pro` | 非思考、流式 | 优先保证中文法律回答质量，同时控制首字延迟 | **已确认** |
| 图谱抽取 EXTRACT | `deepseek-v4-pro` | 非思考 | 入库速度不是关键目标，优先保证实体关系质量 | **已确认** |
| 查询关键词 KEYWORD | `deepseek-flash` | 非思考 | 查询关键路径优先低延迟 | **已确认** |
| Embedding | `BAAI/bge-m3` 本地部署 | 固定版本和维度 | DeepSeek 官方 API 当前未提供 Embedding 接口；LightRAG 官方将其列为可用的本地多语言方案 | **已确认** |
| Reranker | 首轮关闭 | — | 先建立最小基线，后续单独验证重排收益 | **已确认** |

DeepSeek 调用要求：

- 使用官方 OpenAI 兼容地址 `https://api.deepseek.com`。
- 最终回答启用流式输出，用于测量首字延迟。
- 最终结构化结果使用 JSON Output，并在 Prompt 中明确 JSON Schema 和示例。
- 所有查询角色显式关闭默认思考模式，先验证能否满足 P95 首字延迟；思考模式只作为后续独立实验变量。
- 实验运行前调用模型列表接口，记录实际可用模型、返回元数据和测试日期。
- API Key 只通过环境变量或密钥管理注入，不得写入仓库、配置样例或实验日志。
